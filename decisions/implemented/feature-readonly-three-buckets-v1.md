# v1 只读，且只有三个桶

## Problem

PR 面板能做的事很多：评论、approve、merge、建 PR、看 CI、看 diff 行内评论……
一次全做，会把"看"这件事的正确性验证拖进写操作的权限与误操作风险里。

## Decision

v1 **只读**，且只做三个桶：**我提的**（`author:@me`，开着的）、**待我审**
（`review-requested:@me`）、**最近合并**（`is:merged`，最近 20 条）。
点开一行看到的是插件自渲染的完整 PR 内容（正文 / 评论与评审时间线 / 改动文件清单）。

## Alternatives considered

- **先做写操作**：误操作代价高（merge 一个不该 merge 的 PR），且要处理并发与
  权限失败的重试语义。否掉——先证明"看"做对了。
- **四个桶（加"我参与的" / "团队待审"）**：用户已明确 v1 不做"待我团队审"
  （那需要团队/org 语义）；桶越多，每个桶的取数与降级路径都要各自验证。
- **不做合并桶**：合并记录是"我刚做的事有没有落地"的回路，值得留。

## Consequences

- 已知边界写进 README：只支持 `github.com`；需要 `gh` 登录；合并桶是最近 20 条
  而不是时间窗；搜索只在已加载的页内做。
- 写操作留到后续独立批次，且必须带着自己的权限/失败语义设计。
